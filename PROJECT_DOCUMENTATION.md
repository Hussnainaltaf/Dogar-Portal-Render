## 1. What This System Does

This is an end-to-end operations platform for a **licensed overseas-employment
promoter** in Pakistan. It replaces the ledgers, Word templates and WhatsApp
threads that such agencies typically run on, and tracks the complete lifecycle
from a foreign employer's manpower request through to a worker boarding a plane.

The three core objects and how they relate:

```
CLIENT (foreign employer / sponsor)
   │  e.g. a construction company in Riyadh
   │
   └── DEMAND FILE (a manpower request, government-numbered)
          │  "40 masons + 10 electricians for Jeddah, 2-year contract"
          │
          └── CANDIDATE ASSIGNMENT (a worker placed against one trade)
                 │
                 └── CANDIDATE (the worker: passport, medical, visa, protector…)
```

### Who uses it

| Role | Typical user | What they do here |
|---|---|---|
| **Admin** | Agency owner / director | Everything: users, roles, tenants, audit, settings |
| **Manager** | Operations manager | Full operational work; no user/role/tenant/audit access |
| **Staff** | Data-entry clerk | View + create + edit candidates; no deletes, no financials |
| **Super-admin** | Vendor support | Cross-tenant administration (SaaS operator) |

### Why it exists

The work is document-heavy, deadline-driven and legally regulated. A single
candidate involves a passport, medical certificate, Protector of Emigrants
stamp, visa, e-number and ticket — each with its own expiry and its own
government office. Miss a medical expiry and the worker cannot fly. This system
centralises that state, generates the paperwork, and raises reminders before
deadlines lapse.

## 2. Business Domain Primer

Read this section if you are not familiar with Pakistani overseas-employment
operations — the terminology is baked into the data model and the UI.

| Term | Meaning |
|---|---|
| **OEP** | Overseas Employment Promoter — a licensed recruitment agency. Licence number appears on official documents. |
| **Demand Letter / Demand File** | The foreign employer's formal manpower request, attested by their government and the Pakistani mission. The unit of work in this system. |
| **Protector of Emigrants** | Government office (Bureau of Emigration & Overseas Employment) that stamps a worker's passport. **Legally mandatory** — no stamp, no legal departure. Hence `protector` is a first-class workflow stage, not a checkbox. |
| **Protector Letter / Packet** | The document bundle submitted to that office. Generated by this system. |
| **E-Number** | Emigrant number issued after Protector clearance; required for ticketing. |
| **GAMCA / Medical** | Gulf-approved medical centre exam. Time-limited — a common source of costly re-dos. |
| **Visa Stamping** | Embassy stamps the work visa into the passport. |
| **Sponsor** | The employer in the destination country who legally sponsors the visa (`sponsor_name`, `sponsor_id`, and Arabic variants — Gulf paperwork requires Arabic). |
| **Sub-Agent** | Local intermediary who sources candidates and is paid commission. *Not modelled by this system* — the Sub-Agent screen and cashbook were removed on the operator's request (2026-07-30, see §4.11). The term is kept in this glossary because it still appears in day-to-day conversation. |
| **Trade / Job Category** | The occupation requested (mason, electrician, driver…), with per-trade headcount and salary on the demand file. |

**Why Arabic fields exist throughout:** Gulf embassies and sponsors require
names, addresses and occupations in Arabic. The system stores Arabic variants
alongside English and can auto-translate names and occupations (§3.6).

### 4.2 ⚠️ Dual Frontend — read this before editing UI code

The application ships **two complete frontends**, selected by one setting:

| `USE_SPA` | Page routes serve | Location |
|---|---|---|
| `true` **(default)** | Compiled **React SPA** | `app/static/spa/` |
| `false` | **Jinja2** server-rendered templates | `app/templates/` (22 files) |

Both are maintained and both were security-audited. **Editing a Jinja template
will have no visible effect in the default configuration** — a real trap for new
contributors. To work on the Jinja UI, set `USE_SPA=false` and restart.

The `/api/*` layer is shared by both, so backend work benefits each equally.

### 4.3 Request pipeline

Order matters and is deliberate:

1. **TrustedHostMiddleware** — Host-header allow-list (`ALLOWED_HOSTS`).
2. **CORS**.
3. **CSRF** — double-submit cookie; enforced on state-changing requests.
   Deliberately **not** exempting the whole `/api/auth/` prefix: only `login`,
   `forgot-password` and `reset-password` are exempt.
4. **CSP nonce** — fresh per-request nonce injected into `request.state`.
5. **Request ID** — correlation ID threaded into structured logs.
6. **Rate limiting** — slowapi.
7. **Prometheus metrics**.

### 4.4 Technology choices and rationale

| Choice | Why |
|---|---|
| **FastAPI** | Async, automatic OpenAPI, Pydantic validation at the boundary. |
| **SQLAlchemy 2.0** | Same ORM over SQLite (dev, small deployments) and PostgreSQL (scale) with no query rewrites. |
| **SQLite default** | A fresh clone boots with **zero** database setup — important for a product delivered as an archive to non-specialist operators. |
| **Jinja + vanilla JS** | The original UI. No build step, so an operator can patch a page with a text editor. |
| **React SPA** | The modern UI, for responsiveness and deep-linkable client-side routing. |
| **ReportLab + pypdf** | Precise coordinate placement onto scanned government forms — the core of the document engine. |
| **Optional dependencies** | Arabic shaping, Sentry, Redis and Twilio are imported behind `try/except`; the app boots without them and logs what is unavailable. |

### 4.5 Performance: how the list endpoints stay fast

Every optimisation here was **measured before and after**, on realistic data
volumes, and at least one plausible optimisation was **discarded because the
measurement refuted it**. The numbers below are reproducible with
`scripts/benchmark.py` and the migration docstrings.

**Indexed sort keys** (migration `2a4f1b8c9d31`). Profiling the real data volume
showed every list endpoint doing a full table scan plus a temp B-tree sort,
because `created_at` — their default sort key — carried no index:

| Endpoint | Before | After | Gain |
|---|---|---|---|
| reminders feed | 1.66 ms | 0.17 ms | −89% |
| demands list | 0.65 ms | 0.15 ms | −77% |
| clients list | 0.33 ms | 0.12 ms | −63% |

**The candidates list needed a different fix** (migration `3b7d2e4f8a15`). It was
the one endpoint indexes could not help, because its cost was *structural*: it
ordered by a correlated scalar subquery (newest linked demand per candidate), so
the subquery ran **once per candidate row** and SQL `LIMIT` could not prune the
outer scan. A deep page therefore cost as much as page 1, and the cost grew with
the *total* row count. It was **91% of the endpoint's database time**.

The fix denormalises the sort key into an indexed `candidates.latest_demand_id`
column:

| Candidates | Correlated subquery (page 1 / deep) | Now (page 1 / deep) |
|---|---|---|
| 2,675 (real data) | 14.2 ms / 18.4 ms | **1.33 ms / 1.43 ms** |
| 40,000 (synthetic) | 98.9 ms / 317.8 ms | **5.1 ms / 12.7 ms** |

Note the shape, not just the size, of the win: deep-page cost is now
**flat** instead of tripling.

> **An idea that was measured and rejected.** The obvious rewrite — collapsing
> the per-row subquery into a single grouped derived table, `LEFT JOIN`ed once —
> was implemented and benchmarked *first*. It produced byte-identical ordering
> but was consistently **slower** than the subquery it replaced (−12% at 2.5k,
> −13% at 10k, −12% at 40k rows), because it materialises and groups the entire
> assignment table before joining. A window-function CTE was rejected earlier for
> the same reason. Only denormalisation changes the complexity class. This is
> recorded so nobody "simplifies" the query back into a join.

A second, subtler cost was fixed at the same time: expressing *nulls last* as an
`IS NULL` sort term forces `USE TEMP B-TREE FOR ORDER BY` on top of the index
scan (1.85 ms vs **0.13 ms** on a deep page). Emitting a real `NULLS LAST` via
SQLAlchemy's `nullslast()` lets the covering index satisfy the `ORDER BY`
outright. A bare `.desc()` would be marginally faster still, but NULL placement
on `DESC` is dialect-dependent — SQLite and PostgreSQL would paginate
**differently** — so it is deliberately not used.

**Why a denormalised column is safe here.** Denormalisation trades a slow query
for a *correctness* risk: a stale value would make the list silently paginate in
the wrong order rather than fail loudly. That is a worse bug than the slowness it
replaces, so the column is **not** maintained by application code. Candidate
assignments are written through paths that bypass SQLAlchemy's ORM events —
`bulk_save_objects()`, raw SQL, and `cascade="all, delete-orphan"` — so the
column is maintained by **database triggers**, which sit below every one of those
paths. Three independent guards back this up:

1. **Equivalence** — the new ordering was verified identical to the old
   subquery's across all 2,675 rows, and again end-to-end over the HTTP API
   (125 rows across 5 pages: no gaps, no duplicates, demand context intact).
2. **`tests/test_sort_key_integrity.py`** — 12 tests drive all eight mutation
   paths and assert the column still equals the recomputed truth. They are
   mutation-verified: removing the `DELETE` trigger, removing the `UPDATE`
   trigger's old-owner recompute, or flipping NULL placement each **fails** the
   suite.
3. **`scripts/verify_sort_key.py`** — an independent auditor that recomputes
   truth across the control database and every tenant, with `--repair`. Verified
   by injecting drift, confirming precise detection, then repairing back to
   exact truth.

One residual gap is accepted and documented rather than hidden: re-parenting a
`job_category` to a different demand would drift the column. The application
never does this (categories are created and deleted, never moved), and a trigger
on that hot table would tax every write, so the auditor covers the case instead.

**Caching.** List responses are cached per user *and per tenant slug*. The tenant
component is essential, not cosmetic: tenants live in separate databases, so user
IDs are per-tenant autoincrement values and are **not** globally unique. Keying
on user ID alone would let one tenant's cached list be served to another
tenant's same-numbered user when a shared Redis cache is configured.

### 4.9 The Overlay Engine's geometry contract

Every Protector and visa document is produced by drawing candidate data *on top
of* a scan of the real government or bank form at absolute coordinates. Three
rules govern that, and all three are now enforced by tests rather than by
convention:

| Rule | Value | Enforced by |
|---|---|---|
| Coordinate space | A4, **595 × 842 pt**, origin **bottom-left** (ReportLab) | `DocumentTemplate.page_width/page_height` defaults; header of `scripts/seed_document_fields.py` |
| Background fit | `bg_fit` defaults to **`fill`** — the scan is stretched to the full page box | `_draw_background()` in `app/services/pdf_engine.py`; `tests/test_bg_fit.py` |
| Scan aspect ratio | must match the page aspect within **2 %** | `tests/test_background_geometry.py` |

The third rule exists because the first two interact dangerously. `fill` stretches
the scan to the page, but the overlaid text is *never* stretched — it is placed at
its literal coordinate. So a scan whose aspect ratio differs from the page's
produces a document where the printed boxes have slid out from under the values
that belong in them, with the error growing the further you get from the origin.
Nothing raises, nothing logs; the PDF simply comes out wrong.

**This shipped once.** In v1.1.0 `allied_bank_form7.jpg` was 1807 × 2339 px —
aspect 0.77255, which is **US Letter** (0.77273), not A4 (0.70665). Rendered onto
the A4 page it was squeezed horizontally by **8.53 %**. Measured against the seven
seeded fields on that slip, the printed boxes had moved:

| Field | x (pt) | box displaced by |
|---|---|---|
| `full_name`, `cnic`, `address`, `passport_no`, `salary` | 180 | +3.1 pt (+1.1 mm) |
| `phone`, `__today__` | 430 | **−18.2 pt (−6.4 mm)** |

6.4 mm is more than a full line height on a bank deposit slip — enough for a
Protector office to reject the form. The repair was a **lossless crop**: the scan
carried 160 px of pure-white left/right margin, of which 154 px had to go to reach
a true A4 aspect. The crop was applied only after asserting that **zero** ink
pixels fell outside the crop box, giving 1653 × 2339 — which is also the exact
size every other scan in `app/static/pdf_backgrounds/` already used. Verified end
to end by reading the image placement matrix back out of a rendered PDF:
distortion went from **−8.530 %** to **−0.009 %**.

`saudi_visa_application.jpg` (Islamabad visa form) is 1624 × 2339, i.e. **1.75 %
narrow**. That one is accepted as-is and recorded in
`KNOWN_ASPECT_EXCEPTIONS`: the scan is *short* of A4 width rather than over it, so
cropping cannot help, and padding it would move the printed boxes. It is waived
individually rather than by relaxing the global tolerance, so any new off-spec
scan still fails the suite.

> **If you add or replace a background scan**, make it A4-proportioned
> (1653 × 2339 px is the house standard) before committing. `pytest
> tests/test_background_geometry.py` will tell you the exact deviation if not.

### 4.10 Where the designer's field list comes from

The Template Designer palette (what you can drag) and the overlay resolver
(what actually prints) must describe the same set of fields. They are therefore
generated from one rule set, in `app/services/overlay_engine.py`:

| Constant | Meaning |
|---|---|
| `ALIAS_PRECEDENCE` | `("candidate_", "job_", "demand_", "client_")` — most specific first. A short name owned by several tables resolves to the table nearest the document's subject, so `status` on a candidate document means the **candidate's** status, not the client's. |
| `NO_ALIAS_COLUMNS` | Housekeeping columns (`id`, `created_at`, `updated_at`, the `*_by_id` audit columns, `custom_fields`) that are deliberately **not** offered as document fields. |
| `resolvable_short_keys()` | Enumerates every short field key derivable from the ORM models, mapped to its palette group. |

`resolve_overlay_fields()` applies those rules to fill in short aliases, and
`designer_palette()` ends with a **completeness sweep** over
`resolvable_short_keys()`. The sweep only ever *adds*: curated labels, grouping
and render types defined earlier in that function always win.

**The practical consequence: adding a column to `Candidate`, `Demand`,
`JobCategory` or `Client` makes it draggable in the designer automatically.**
No palette edit is needed, and none should be added just to expose a column.

#### This shipped once

Both sides used to be hand-written lists, maintained independently, and they had
drifted apart in *both* directions:

- **145 columns resolved but were not draggable.** They held real data that
  simply could not be placed on a form. `Client.sponsor_id` ("Sponsor ID") and
  `Demand.bataka_number` ("Bataqa No.") were among them — operators worked
  around it by dropping a static text box, which then printed the literal
  placeholder text onto the Saudi visa form.
- **60 palette entries resolved to nothing.** A field dragged from one of those
  rendered permanently blank, with no error in the UI, the logs or the PDF — so
  it looked like missing *data* rather than a missing *mapping*.

A third, related defect: the whole `customer_*` (agency profile) block was
skipped when no `company_settings` row existed, silently dropping all 21 tenant
fields. That is every fresh install. Those keys are now always defined, so an
empty value means "not configured" rather than "field does not exist".

`tests/test_designer_palette.py` fails if either half of the contract is broken
again — including a by-name guard for the two fields above.

### 4.10.1 Character combs: multi-row rows, word breaks, and real capacity (2026-08-12)

A **character comb** (`render_type: "char_cells"`) prints one character per
pre-printed box. It is the most defect-prone field type in the system because a
single field's geometry is consumed by **three independent renderers** that must
never disagree:

| Renderer | File | What the operator sees |
|---|---|---|
| PDF | `app/services/pdf_engine.py` → `_draw_char_cells()` | The downloaded / printed PDF |
| HTML print | `app/api/endpoints/documents.py` (print path) | The browser **Print** button |
| Designer | `app/frontend/src/pages/designer/FieldMarker.tsx` | The drag-and-drop overlay |

**Every fix to comb geometry must land in all three.** Historically it did not,
and the divergence is what hid the defects listed below: the designer looked
correct, so the field was signed off, and only the printed paper was wrong.

#### The `meta` contract

| Key | Meaning |
|---|---|
| `cell_count` | The number of **characters** the row holds. **Not** the number of printed slots — see `group_sizes`. |
| `cell_width` | Width of one printed box, in points. |
| `cell_gap` | Gap between adjacent boxes, in points. Pitch = `cell_width + cell_gap`. |
| `group_sizes` | Grouped comb: the printed boxes come in clusters separated by a wider gap or a dash. CNIC is printed **5-7-1**, so its 13 digits occupy **15 slots**. |
| `char_offset` | Continuation row of a multi-row comb: skip this many leading characters of the value. |
| `format` | `"text"` **keeps spaces**; every other format strips them. |
| `draw_boxes` | Whether the renderer draws its own boxes (blank stock) or relies on the pre-printed scan. |

#### `group_sizes`: slot span ≠ character count

The true width of a grouped comb is `slot_span × pitch`, where `slot_span`
accounts for the separator slots. For the CNIC comb: 13 characters, `group_sizes
= [5, 7, 1]`, **slot span 15**. Any code that computes width as `cell_count ×
pitch` is wrong by two whole cells and pushes the last digits outside their
boxes. The designer's auto-fit (`refitCellMeta`) was group-blind and did exactly
this.

#### `char_offset`: the multi-row rule

A value longer than one printed row is bound **twice** — two rows of the same
`field_key`, distinguished only by `char_offset`:

> **`char_offset` on a continuation row must equal the previous row's
> `cell_count`.** Anything else silently repeats or drops characters.

This has a consequence for every piece of code and every test that looks up "the
row for field *X*": **it must be offset-aware.** Selecting "the first match" or
"the lowest *y*" picks an arbitrary row. `tests/test_fresh_install_geometry.py`
uses `_primary_page1_rows()`, which selects on `char_offset` being absent or
zero — a genuinely *cloned* field has no offset either, so it still shows up as
an extra row and still fails.

#### `format: "text"` and word breaks

Name and address combs need a **blank box between words**, otherwise
`MUHAMMAD IMRAN` prints as `MUHAMMADIMRAN` and every character after the space
sits one box to the left of its printed position. Only `format: "text"` preserves
the space. Shipping the *support* for this without setting it in the template
snapshot is a silent no-op, so `tests/test_print_geometry.py` asserts the shipped
snapshot value, not just the code path.

#### Real capacity vs real data

Capacity is a physical property of the pre-printed paper. A PIL scan of
`oep_form_p1.jpg` finds rules at `y_pt` **397.0 / 416.5 / 436.0** — that is
**two** address rows, and no third row exists to bind:

| Field | Printed capacity | Data that exceeds it |
|---|---|---|
| `full_name` | 2 rows × 14 = **28** chars | 4 of 2,675 (0.1 %); longest 32 |
| `address` | 2 rows × 13 = **26** chars | **2,198 of 2,636 (83.4 %)**; median 35, 90th pct 52, longest 91 |

**The address comb is a paper limitation, not a bug.** The engine truncates at
capacity and logs an overflow warning on the `dtc.pdf_engine` logger. It cannot
be fixed by adding a third row because the form has only two. The options are a
smaller cell pitch (illegible), an abbreviation policy applied at data entry, or
printing the address as free text in the margin. **This decision belongs to the
business, not to the code**, and is recorded in §18.

#### How comb geometry is verified

Measurement, never estimation:

- `pytest tests/test_print_geometry.py` — section 9 executes the **real**
  `FieldMarker.tsx` and `engine.ts` through `esbuild` + `react-dom/server`, and
  drives the real print endpoint, so a regression in any of the three renderers
  fails the suite. These four tests were themselves mutation-tested; the first
  versions were **vacuous** (they matched a helper *name* in the source, which
  survived a mutation that gutted the helper's body) and were replaced with
  behavioural ones.
- `python scripts/verify_comb_geometry.py` — opens the print page in **Chromium**
  and reads `getBoundingClientRect()` for every character span, comparing the
  measured centre against the declared pitch (tolerance = pitch / 4). Last run:
  11 combs, **worst deviation 0.02 pt**.

> The verifier reports blank cells as occupied. Skipping whitespace-only spans
> while using the array index as the cell index shifts every character after a
> space by exactly one pitch — which is how an earlier version of the probe
> "found" a 29.35 pt error in a comb whose real worst offset is 0.01 pt. A
> measurement tool needs its own regression story.

- `python scripts/verify_dialog_geometry.py` — opens **every dialog in the app**

  `BELOWFOLD` (reachable by scrolling — poor, not broken) **separately**, and

  detect it: with `.page-enter`'s `both`/`will-change` and the Roles portal
  reverted, the script reports `CLIPPED Roles / Customize Role` and exits 2,

  crying wolf. Last run: **11 dialogs, PASS**.

> This script is also how the missing `role="dialog"` attributes were found. It
> locates dialogs via `[role=dialog]`, and the two overlays that had actually
> been broken were *invisible to it* — because neither declared the role. The
> two dialogs the operator could not use were also the two that assistive
> technology announced as anonymous `div`s. A measurement tool that silently
> skips its own subject reports a clean run; make the harness prove it opened
> what it claims to have opened (`opened=N` in the output).

- `python scripts/scan_committed_secrets.py [--check|--json]` — the **secret
  ratchet**. Walks the whole tree (hidden files included, plus the built SPA
  bundle) and fails on: known-compromised credential literals, any live `.env`
  secret value appearing outside `.env`, or a hardcoded
  `password = "literal"` assignment. `--check` exits 1 on any finding and is
  what `tests/test_no_committed_secrets.py` runs. See §14.4 for the incident
  that motivated it. Last run: **0 findings**.

- `./venv/bin/python scripts/rotate_bootstrap_passwords.py [--dry-run]
  [--keep-secret-key] [--print-admin-password]` — rotates the bootstrap admin
  and vendor credentials through the app's own `User` model, rotates
  `SECRET_KEY` (which is what actually revokes existing sessions — see §14.4),
  revokes outstanding `password_reset_tokens`, writes the new values into `.env`
  at mode 0600, and prints only SHA-256 fingerprints. Restart the app afterwards
  (`pm2 restart dogar-portal`) so the new `.env` is loaded.

### 4.10.2 Fields bound on the OEP form that have no data (2026-08-12)

Measured over all **2,675** candidate records. A field printing blank has three
*different* root causes, and they need three different fixes — the distinction is
the point of this table:

| Field | Populated | Wizard input | Diagnosis |
|---|---|---|---|
| `next_of_kin_nic` | 2,164 / 2,675 (80.9 %) | `AssignWizard.tsx:452` | Optional at entry — data gap |
| `permission_date` | 2,238 / 2,675 (83.7 %) | `AssignWizard.tsx:441` | Optional at entry — data gap |
| `next_of_kin_name` | 2,331 / 2,675 (87.1 %) | `AssignWizard.tsx:451` | Optional at entry — data gap |
| `next_of_kin_relation` | 2,337 / 2,675 (87.4 %) | `AssignWizard.tsx:453` | Optional at entry — data gap |
| `passport_issue_place` | **0 / 2,675 (0.0 %)** | `AssignWizard.tsx:425` | **Collectable but never used.** The input exists and works; no operator has ever filled it. A process/training fix, not a code fix. |
| `email` | **0 / 2,675 (0.0 %)** | **none anywhere → FIXED 2026-08-12** | **Could not be entered at all.** Bound on the OEP form, displayed read-only at `Candidates.tsx:610`, resolved correctly by the overlay engine, accepted by the backend — but no `<input>` existed anywhere, so it was blank by construction. An input and a `STEP_FIELDS` entry were added to step 1 of the wizard. |

Not placed on any template at all: the **Funds and Fee Details** table (6 × 6,
form fields 23–28). Nothing is broken; the region is simply unbound.

#### The collectability contract

The `email` defect was invisible to every existing check, and the reason
generalises. Geometry checks, the background-scan checks and the unbound-field
audit can all only inspect fields that **exist and resolve** — and `email` did
both, perfectly. The missing half was the **data-entry path**, which no test
looked at. Nor can data alone distinguish the two 0 % cases: `passport_issue_place`
and `email` were statistically identical, but one needed operator training and
the other needed code. Only the presence or absence of an input tells them apart.

So the guard is structural:

> **Every `Candidate` column bound on a shipped template must appear in the
> wizard's `STEP_FIELDS` map.**

`STEP_FIELDS` is the authoritative list, not the rendered inputs: the wizard
PATCHes each step using it and `finalize()` flat-merges those slices, so a key
absent from it is never transmitted **even if an input is on screen**. A test
that merely looked for an `<input>` would pass while the typed value was
silently discarded.

`tests/test_template_field_bindings.py` enforces this, and — because a check
that only ever asserts an empty list is indistinguishable from a broken parser —
also proves the detector fires and that its regex still matches the real map.
Both guards were mutation-tested by re-introducing the shipped defect and its
subtler input-present/key-absent variant; both fail the suite.

### 4.10.3 Address capacity policy: what prints when the address does not fit (2026-08-14)

§4.10.1 established how a multi-row comb is *measured*. This section states what
the system **does** when the measurement says the value cannot fit — the case
that applies to the overwhelming majority of real records.

#### The measurement

The OEP address comb holds **26 characters**, not 13 and not 52:

| Field | `y` | `cell_count` | `char_offset` | `cell_width` | `format` |
|---|---|---|---|---|---|
| `template_geometry.json` fields[4] — Address | 420.00 | 13 | 0 | 31.47 | `text` |
| fields[24] — Address (row 2) | 400.36 | 13 | 13 | 31.45 | `text` |

Capacity is `max(char_offset + cell_count)` across the rows sharing a
`field_key`, **never** `sum(cell_count)`. Summing is not a stylistic
preference: a duplicated row that is missing its `char_offset` sits at offset 0
and overprints row 1, so real capacity is 13 while the sum claims 26. The `max`
rule reports the bug; the `sum` rule hides it. `comb_capacity_for_key()`
implements `max`, and `tests/test_comb_capacity.py` pins the distinction.

#### The data

Measured over all **2,675** candidate records with a stored address:

| Metric | Value |
|---|---|
| Over 26 characters | **2,231 / 2,675 — 83.4 %** |
| Median length | 35 |
| 90th percentile | 52 |
| Maximum | 91 |
| Fit as stored | 438 (16.6 %) |
| Fit after attested abbreviation | 517 (19.6 %) |

The pre-2026-08-14 behaviour on the real value
`HARI PURKI P.O KAMONKI TEHSIL KAMON KI DISTT GUJRANWALA` was a blind 26-character
slice: it cut **mid-word** and silently dropped the district. On a government
submission form that is not a cosmetic defect — it is a wrong address printed
with no indication that anything was lost.

#### The policy

One decision point, `app/services/comb_capacity.py::fit_comb_text()`, applied as
an ordered ladder. Every renderer reaches it through
`resolve_comb_row()`; none of them re-implements any part of it.

| Stage | Condition | Status | What prints |
|---|---|---|---|
| 0 | value empty / whitespace-only | `empty` | nothing |
| 0 | `capacity <= 0` (misconfigured field) | `capacity_exceeded` | nothing, with a "fix the field in the Template Designer" reason |
| 1 | `len <= capacity` (**including exactly 26**) | `fits` | the value, unmodified |
| 2 | attested abbreviations bring it within capacity | `abbreviated` | the abbreviated form |
| 3 | a **word boundary** exists at or before capacity | `truncated_at_word` | the kept words — never a partial word |
| 4 | the first word alone exceeds capacity | `capacity_exceeded` | **nothing** |

Stage 4 prints nothing deliberately. A mangled fragment of an address looks
like a real address and will be acted on; a blank comb with a review flag will
not.

#### Attested abbreviations only

An abbreviation is legitimate here **only if the operators' own data already
contains the short form**. That rule is not aesthetic — an invented
abbreviation is an invented address. Counted across the live address column:

| Long form | Short form | Uses of the short form | Verdict |
|---|---|---|---|
| `TEHSIL`, `TEH.` | `TEH` | 231 | **attested** |
| `DISTRICT`, `DISTT.`, `DIST`, `DIST.` | `DISTT` | 151 | **attested** |
| `MOHALLAH`, `MOHALLA`, `MOH.` | `MOH` | 458 | **attested** |
| `P.O`, `P.O.`, `POST` | `PO` | 135 | **attested** |
| `STREET` | `ST` | 140 | **attested** |
| `VILLAGE` | `VILL` | 44 | **attested** |
| `ROAD` | `RD` | **0** (against 233 uses of `ROAD`) | **rejected** |
| `NUMBER`→`NO`, `HOUSE`→`H`, `NEAR`→`NR`, `COLONY`→`COL`, `TOWN`→`TWN` | — | 0 | **rejected** |

`REJECTED_ABBREVIATIONS` in the module is documentation of what was considered
and refused; the behaviour comes from `ATTESTED_ABBREVIATIONS`. A test asserts
the two agree, because a table that only documents can rot silently.

Abbreviation is honestly marginal: it moves fit from 438 to 517 records — **+79**
— leaving **80.4 % still over capacity**. That is precisely why the
review-required state is the primary mechanism and abbreviation is only a
courtesy applied first.

#### Source data is never touched

`CombFit.canonical` carries the full stored address unchanged (whitespace
normalised only); `CombFit.printed` carries the print representation. Nothing in
this path writes to the database. The record keeps the complete address forever;
only the *rendering* is reduced, and the reduction is reported.

#### The three renderers agree by construction

| Path | Entry point |
|---|---|
| PDF (ReportLab) | `pdf_engine.py::_render_field` → `resolve_comb_row()`, drawn with `pre_resolved=True` |
| HTML / print | `api/endpoints/documents.py` char_cells branch → `resolve_comb_row()` |
| Designer preview | `_build_overlay_payload` emits `comb_row` / `comb_fit`; `FieldMarker.tsx` renders the server's decision |

The designer contains **no TypeScript re-implementation** of the policy. This
matters because the three paths have already diverged twice in this project
(§4.10.1): the HTML path lacked comb support until 2026-08-11, and the designer
drew combs as one continuous string until 2026-08-12. A shared decision function
is the only structural fix.

`pre_resolved=True` exists because `_draw_char_cells` used to re-strip and
re-slice the text it was handed. A continuation row legitimately **begins with a
space** — the blank box between two words — and `.strip()` eats it, shifting
every later character one cell to the left. Under `pre_resolved` the policy's
decision is drawn verbatim.

`resolve_comb_row()` imports `normalize_cell_value` from `pdf_engine` *lazily,
inside the function body*, because `pdf_engine` imports this module at top level.

#### What the operator sees

A row whose status is `truncated_at_word` or `capacity_exceeded`
(`REVIEW_REQUIRED_STATUSES`) renders a badge in the designer preview carrying
`data-comb-review="<status>"` — amber for a word-boundary truncation, red
(`#dc2626`) for capacity exceeded — with the human reason on hover. Both server
paths also log the reason at WARNING. Nothing is dropped silently.

#### Verification

`tests/test_comb_capacity.py` — 60 tests: boundary cases (empty / short /
exactly-26 / 27 / single over-long word / zero cells), canonical-never-modified,
attested-vs-rejected, word-boundary truncation, `max` vs `sum` capacity, row
partitioning and the preserved leading space, the `resolve_comb_row` contract,
three-path agreement, and pinning of the shipped template geometry. The PDF test
asserts on the **x-coordinates passed to `drawCentredString`** and reconstructs
each cell, so a one-cell shift is caught, not just a wrong glyph.

**23 mutations, 23 caught.** Two of those mutations initially *escaped* and both
exposed a real weakness in the tests, not a false alarm:

* Renaming `ROAD` in `REJECTED_ABBREVIATIONS` escaped because the test was
  parametrised **over the very table it guarded** — editing the table just
  changed what got tested. Fixed with a hardcoded `MUST_NOT_ABBREVIATE` list in
  the test file.
* Ignoring `pre_resolved` escaped because the test spied on the text *entering*
  `_draw_char_cells` and so could not see a `.strip()` *inside* it. Fixed by
  asserting on what is actually drawn.

### 4.12 RBAC: how a permission key becomes real (2026-07-31)

`PERMISSION_CATALOG` in `app/core/permissions.py` drives the Roles editor —
every key it declares is rendered as a tickable checkbox. A key that no code
path *reads* is therefore worse than useless: it tells the operator they have
granted or withheld a capability when in fact nothing changed.

An audit on 2026-07-31 measured this directly and found **22 of the 44 keys —
exactly half the catalogue — were declared but enforced nowhere.** The
measurement is worth recording because the obvious version of it is vacuous:

> Grep every catalogue key across `app/**/*.py`. **You must exclude
> `app/core/permissions.py` itself** — otherwise the catalogue satisfies every
> key it declares and the check reports `0 dead` regardless of reality. The
> first run of this check did exactly that and reported a clean bill of health.

This was not merely cosmetic drift. Three concrete escalations were reproduced
against a live Staff token whose permission set contained no `settings:*`,
`depositors:*` or `receipts:*` keys at all:

| Reproduced with a Staff token | Result before the fix |
|---|---|
| `POST /api/lookups/cities` | **200** — created City id 57 |
| `POST /api/lookups/depositors` | **200** — created a depositor |
| `POST /api/demands/1/payments` | **200** — **issued financial receipt `RCP-2026-0001`** |
| `POST /api/documents/admin/dedupe-all-fields` | **200** — mutates *every* document template |
| `GET /api/protector-letters/demand/{id}/packet` | **200** — printed a demand packet on company letterhead |

All probe artefacts were deleted afterwards (payment removed and the demand's
`total_credit` re-verified at `0.0`; city 57 dropped).

#### What changed

* **`settings.py`** — `PUT /general` moved from `require_admin` to
  `require_permission("settings:company")`. This was the finding as reported,
  though the reported *direction* was backwards: the complaint was that a
  Manager holding `settings:company` could not edit, whereas the live problem
  was that the key was inert and the route was separately reachable.
* **`lookups.py`** — all lookup **writes** now require `settings:lookups`;
  depositor reads require `depositors:view` and writes `depositors:edit`.
* **`tenants.py`** — the local `_admin_only()` helper was a bare
  `user.role != "admin"` string comparison. It now resolves through
  `user_permissions()` and takes the key as a parameter (`settings:tenants`,
  or `settings:branding` for the three logo/letterhead routes). This also
  fixed a latent bug: a **super-admin whose `role` column was not literally
  `"admin"` was refused**, even though `user_permissions()` grants them `"*"`
  everywhere else in the codebase.
* **`users.py`** — nine admin routes moved onto `users:view|create|edit|delete`,
  `roles:view|edit` and `loginhistory:view`. Nothing was *opened up* here: they
  were already admin-locked, which is stricter than the catalogue. The keys were
  decorative.
* **`demands.py`** — six ungated writes gated, including **both** payment
  endpoints (`receipts:create`), the assignment mutations
  (`candidates:assign`) and category creation (`demands:edit`).
* **`documents.py`** — the two dedupe endpoints gated on `documents:designer`;
  `/templates/{id}/generate` and `/templates/{id}/print` on `documents:print`.
* **`candidates.py`** — the three photo-upload routes gated on
  `candidates:edit`; the checklist routes on `candidates:documents`;
  `/print-profile` on `candidates:print`.
* **`protector_letters.py`** — seven `/demand/{id}/…` letterhead routes were
  behind bare `get_current_user`. They now require `demands:print`
  (*"Print demand documents"*), which is the catalogue's own name for exactly
  that capability; the `/print/*` routes render the Protector-of-Emigrants
  packet and keep `protector:print`.
* **35 read routes** across `dashboard`, `clients`, `candidates`, `demands` and
  `documents` moved from plain authentication onto their module `*:view` key.

#### Field-level authorisation

Three catalogue keys describe capabilities that arrive on a route *shared* with
a lower privilege, so no `Depends()` guard can express them:

| Key | Lives on | Distinguished by |
|---|---|---|
| `candidates:stage` | `PUT /api/candidates/{id}` | the payload changes `status` |
| `protector:edit` | `PUT /api/candidates/{id}` | the payload changes `protector_no`, `protector_date` or `e_number` |
| `candidates:export` | *(no route existed)* | a new `GET /api/candidates/export.csv` was added |

For the first two, the route carries the coarse key (`candidates:edit`) as a
dependency and calls the new imperative helper
`assert_permission(user, db, *perms)` once the payload has been parsed. It
shares its resolution logic — and therefore its `"*"` wildcard behaviour —
with `require_permission`, so Admin and super-admin are unaffected.

`candidates:export` had no endpoint at all. Rather than delete a key the
business clearly wants, a real CSV export of the candidate register was
implemented behind it. It is a Manager capability, not a Staff one, because a
full-register download is bulk data egress.

#### Deliberate carve-out

Reads of the **generic** lookups (`cities`, `trades`, `embassies`, …) stay on
plain authentication rather than a permission key. The candidate and demand
forms need them to populate dropdowns, Staff legitimately holds
`candidates:create`, and the catalogue has no `lookups:view` key to gate them
with. `tests/test_rbac_enforcement.py` asserts these reads still return 200 for
Staff, so if someone later gates them the decision has to be made explicitly
rather than by accident.

#### The regression guard

`tests/test_rbac_enforcement.py` locks all of this down:

* `test_every_catalogued_permission_is_actually_enforced_somewhere` re-runs the
  drift measurement on every CI run, with the exclusion described above.
* `test_the_drift_detector_is_not_vacuous` asserts the corpus is non-trivially
  large and that a bogus key is reported — so a broken glob cannot make the
  guard silently pass. Verified by mutation: injecting a fake
  `demands:teleport` key into the catalogue fails the suite.
* `test_role_presets_only_reference_real_keys` catches a preset that survives a
  key rename.
* A parametrised behavioural test replays each escalation in the table above
  and requires **403**.

The catalogue now stands at **44 keys across 10 modules, all enforced.**

### 4.13 SPA design system & shell (2026-08-01)

Applies to the React SPA only (`USE_SPA=true`, the default). Nothing in this
subsection touches routing, API contracts, permissions or tenancy.

#### Token layer

`app/frontend/src/index.css` defines the whole visual identity in four solid
tokens plus three layout metrics:

```css
:root {
  --brand-solid: #1d4ed8;  --brand-solid-hover: #1a44bd;
  --brand-tint:  #eff4ff;  --brand-rule:        #dbe4f5;
  --brand-on-solid: #ffffff;
  --sidebar-w: 15rem; --sidebar-w-collapsed: 4.75rem; --topbar-h: 4rem;
}
.theme-forest-green { --brand-solid: #15803d; --brand-solid-hover: #126b34;
                      --brand-tint: #eefaf1;  --brand-rule: #d3ecdb; }
```

**The tokens are flat on purpose.** A gradient-based pass was written and then
reverted: it read as consumer decoration on a business tool. If you are tempted
to reintroduce a gradient, note that the theme switcher only overrides these four
variables — a gradient hard-codes stops that `.theme-forest-green` cannot reach,
so the alternate theme silently breaks. Use `--brand-solid` / `--brand-tint`.

The Tailwind `blue` palette is virtualised through `withVar()` onto RGB-channel
variables, which is why theme switching needs no per-component work.

#### Shell composition

```
AppLayout
├── Sidebar            layout/Sidebar.tsx      ← NAV_SECTIONS, memoized rows,
│                                                persisted collapse rail
├── Topbar             layout/Topbar.tsx       ← memo(), consumes GlobalSearch
│   └── GlobalSearch   layout/GlobalSearch.tsx ← one impl, two variants
├── Breadcrumbs        layout/Breadcrumbs.tsx  ← band, fed by routeMeta.ts
└── <div key={pathname} className="page-enter"> … route element … </div>
```

* `layout/navConfig.ts` exports `NAV_SECTIONS` (four labelled bands) **and** a
  flattened `NAV` for backwards compatibility. Menu membership is unchanged from
  the pre-2026-08-01 build.
* `layout/routeMeta.ts` → `resolveRouteMeta(pathname)` returns the crumb trail
  for a path. Detail pages override the leaf label at runtime via
  `useCrumbLabel(value)` so a breadcrumb shows *"ZBot Client 9499"*, not an id.
* `key={pathname}` on the content wrapper remounts the pane per navigation,
  which is what makes the `page-enter` animation fire.

#### Constraints you must respect when editing UI

1. **No inline `<style>` blocks.** The live CSP is
   `style-src-elem 'self' 'nonce-…'` — a `<style>` element without the nonce is
   blocked. Inline `style={{}}` *attributes* are allowed
   (`style-src-attr 'unsafe-inline'`), which is why the Toast colours are still
   inline while its layout moved to classes. Note this applies to the **shell**
   only — the standalone document renders run under `style-src-attr 'none'`
   (§7.3.1), and any style attribute they emit is hoisted into a nonced
   `<style>` element at render time.
2. **Modals and sheets must be portalled to `document.body`.**
   `header.topbar` carries `backdrop-filter`, which creates a containing block —
   a `position: fixed` descendant is trapped inside the header instead of
   covering the viewport.
3. **Outside-click dismissal uses `pointerdown`, not `click`.** React 18
   delegates synthetic events to the root container, so a document-level `click`
   listener fires *after* React has already re-rendered and can immediately
   reclose what the user just opened.
4. **Animate opacity and transform only.** `page-enter` is 140ms / 4px rise;
   everything is wrapped by a `prefers-reduced-motion: reduce` block that
   disables it.

### 4.14 Placing fields on pre-printed forms — method, defects found, and how they are now guarded (2026-08-03)

Every "form" template overlays text onto a **scan** of a real government or bank
form. There is no layout engine: a field is correct only if its coordinates were
measured against that scan's printed rules. This subsection records the method,
the two defects found, and why they are now regression-tested.

#### The coordinate contract (see also §4.9)

ReportLab's origin is bottom-left. A field's `y` is the **bottom** of its box, so
the box top is `y + height` and text flows from the top:

```
text_baseline_y = y + max(height - font_size, 0.0)
```

For `char_cells` fields, `y` is used **directly as the baseline**.

**Convention adopted 2026-08-03:** store `height = font_size`. Then
`y` *is* the baseline for both field types, which removes an entire class of
off-by-one-font-size arithmetic mistakes.

#### How coordinates are measured

Rasterise the background JPG into the template's page box (595x842 for A4) at
300 dpi so image rows map linearly onto PDF points, then:

1. Find **horizontal rules** by dark-pixel *row* projection, restricted to the
   value column (clear of the left-hand labels).
2. Find **vertical cell rules** by dark-pixel *column* projection within each
   row band — this yields a grid's cell count and pitch.
3. Convert with `pdf_y = page_height - image_row / scale_y`.
4. Baseline = the band's lower rule + **3.4 pt** (the offset measured from
   printed specimen text on the Allied Bank form).

**Two pitfalls, both of which caused wrong output before being understood:**

- **A dark-fraction threshold that is too high misses rules.** At 0.55 over the
  full page width, three lighter/shorter rules on the OEP form (374.93, 269.83,
  253.75) were not detected. A single missed rule shifts *every* band boundary
  below it by one row. Re-measuring at **threshold 0.40 over x 300..560** found
  them.
- **A label is not vertically centred on its own value box.** On this artwork the
  label text sits level with the **top** of its value box, so pairing a label to
  the band containing the label's centre selects the band one row **too high**.

**The rule that matters more than either:** a baseline falling "inside a printed
box" proves nothing about *which question* that box belongs to. Only rendering
the PDF and reading the ink proves placement. Overlaying the measured rules onto
the artwork (labelled with their `y` values) makes the label→band pairing
directly readable and is the fastest way to get it right.

#### Defect 1 — OEP Form page 1: 11 of 13 fields on semantically wrong rows

`scripts/seed_document_fields.py` placed the whole of OEP page 1 on a lazy 30 pt
ladder descending from `y=735` at a constant `x=150` (its own docstring called
these "best-effort approximations"). An earlier repair corrected three rows by
checking each baseline fell inside *a* box — too weak a check to catch this.
Rendering the live PDF and mapping every baseline against the measured rules
showed:

| Field | Landed on | Should be |
|---|---|---|
| `cnic` | row 2 "Name of OEP/Agency" | row 8 "Emigrant CNIC No." |
| `address` | row 6 "Name" | row 12 "Address (In Pakistan)" |
| `email` | row 7 "Father's / Husband's Name" | row 11 "E-mail" |
| `passport_no` | row 4 "Permission No." | row 17 "Passport No." |
| `next_of_kin_name` | row 8 "Emigrant CNIC No." | row 20 "Name of Nominee" |
| `full_name`, `father_name` | on top of a rule, no row at all | rows 6 / 7 |
| `__today__` | inside the "Funds and Fee Details" fee table | row 1 "Date" |
| `date_of_birth`, `passport_expiry_date`, `nationality`, `profession` | OEP **agency** office-use rows | no page-1 question — removed |

So the emigrant's CNIC printed on the agency-name line, the address on the name
line, the e-mail on the father's-name line, and candidate data printed into
office-use fields an agency official fills in. Every one is mandatory on a
government form.

**Fixed** by `scripts/fix_oep_page1_geometry.py`, which carries the full
measurement table, re-homes all 11 fields, converts rows 6/8/10/12/17 to their
real character grids (14 / 15 / 13 / 13 / 13 cells), deletes the four orphans,
is idempotent, and **exits non-zero if it changed nothing** so a silent no-op
cannot masquerade as success.

**Verified** by generating the PDF through the live HTTPS API and reading the
rasterised page — not by static analysis. Rows 1, 6, 7, 8, 10, 12, 16, 17, 20
and 22 each confirmed to carry their value inside their own labelled box.

**Guarded** in `tests/test_fresh_install_geometry.py`: all 11 coordinates pinned
against the shipped snapshot *and* against a real fresh install; the legacy
ladder named and excluded generically (`x=150`, `y=735-30n`) so it stays
meaningful as more rows are pinned; the four orphans' **absence** asserted; and
`draw_boxes` asserted False on every page-1 grid (True double-strokes cell rules
the form already prints). Mutation-tested: reintroducing the ladder, restoring
an orphan, and flipping `draw_boxes` are each caught.

`char_cells` rows also mean `field_key` is **not** unique within a template —
compare fields by full signature multiset, never by `field_key` alone.

#### Defect 2 — the geometry snapshot could never have shipped

Alembic migrations create **zero** document templates or fields. Correct
geometry reaches a new install *only* via `seed_document_templates()` reading the
shipped snapshot `app/data/template_geometry.json`.

`.gitignore` line 12 read `data/`. **Gitignore patterns without a leading slash
match a directory of that name at any depth**, so `data/` silently excluded
`app/data/` as well as the intended repository-root `data/`. The snapshot could
never be committed, `_verified_template_geometry()` would find no file on a
fresh clone, and seeding would fall back to the legacy approximate layout —
reproducing the exact defect the snapshot exists to prevent.

**Fixed** by anchoring the pattern to `/data/`, with a comment recording why the
slash is load-bearing. Verified both directions: `app/data/template_geometry.json`
is no longer ignored; `data/dogar_trading.db`, `data/tenants/` and `.env` still
are. Release ZIPs were never affected — `make_release_zip.sh` uses a
root-anchored `-x "data/*"`.

**Guarded** by three tests that ask git itself. One gotcha is itself
load-bearing: `git check-ignore` reports a **tracked** path as "not ignored"
regardless of `.gitignore`, so without `--no-index` the assertion silently
degrades into "is this file in the index?". The first version of this guard did
not catch the reintroduced bug for exactly that reason; with `--no-index` it
does.

## 7. Security Posture

This section reflects an external security audit (2026-07-26) and its
remediation. Full detail: **`AUDIT_RESPONSE_2026-07-26.md`**.

### 7.1 Audit outcome

| Finding | Severity | Status |
|---|---|---|
| Stored XSS in templates | HIGH | ✅ Fixed — 62 sinks, CI-enforced |
| `style-src 'unsafe-inline'` | MEDIUM | ✅ Closed — narrowed to `style-src-attr`, accepted on browser measurement (§7.3), then **eliminated entirely** on the standalone document routes (§7.3.1) |
| Password reset gated on SMTP | LOW | ✅ Improved |
| **Account enumeration on reset** | **HIGH** | ✅ Fixed — *found in-house, not in the audit* |

### 7.2 Cross-site scripting — remediated and ratcheted

The audit reported 4 sinks. A purpose-built static analyzer
(`scripts/scan_xss_sinks.py`) enumerated **248** interpolations reaching
`innerHTML`, of which **62** were genuinely unescaped. All are fixed; the
scanner reports **0** and fails CI on regression.

Two sink classes exist, and the second is easy to miss:

1. Template literals — `el.innerHTML = \`<td>${v}</td>\``
2. String concatenation — `el.innerHTML = '<span>' + v`

Each detection pass has its **own mutation probe** in
`tests/test_xss_sinks.py`, because a probe that only mutates a template literal
would keep passing if the concatenation pass were removed.

**Escaping is per-interpolation, deliberately not whole-tree sanitisation.**
The sanitiser strips `on*` handlers, but templates *depend* on inline `onclick`
(rebound by `csp_rebinder.js` to satisfy strict `script-src`). Sanitising whole
trees would strip the handlers and break the app.

**`esc()` vs `escJs()` — a correctness trap, test-enforced.** A value inside a
single-quoted JS string in an `on*=` handler **must** use `escJs()`. `esc()`
emits `&#39;` for an apostrophe, which the eval-free rebinder tokenizer cannot
decode — so the wrong choice is both a security hole *and* a functional break:
a client named `O'Brien & Co` would break the buttons in its own table row.

> **Superseded by the React SPA.** The escaper module described above
> (`app/static/js/safe_dom.js`) belonged to the retired Jinja frontend and no
> longer ships. In the SPA, React escapes interpolation automatically and the
> single audited raw-markup boundary is
> **`app/frontend/src/lib/sanitizeHtml.ts`**; `scripts/scan_xss_sinks.py` scans
> `app/frontend/src` and errors out if its scan roots ever resolve to nothing.

### 7.3 Content Security Policy

Live header. The style directives are **per-response** since 2026-08-04: a
response whose inline style attributes have been hoisted (§7.3.1) gets the
strict variant, everything else keeps the accepted exception.

```
default-src 'self'
script-src      'self' 'nonce-<per-request>'    ← strict
style-src-elem  'self' 'nonce-<per-request>'    ← strict

  # standalone documents (hoisted) — 2026-08-04
style-src-attr  'none'                          ← ZERO exceptions
style-src       'self' 'nonce-<per-request>'    ← legacy fallback, also strict

  # Jinja shell / SPA shell (not hoisted)
style-src-attr  'unsafe-inline'                 ← ACCEPTED (proven inert)
style-src       'self' 'unsafe-inline'          ← legacy fallback only

object-src      'none'                          ← added 2026-07-28
base-uri        'self'                          ← added 2026-07-28
form-action     'self'                          ← added 2026-07-28
font-src 'self' data: · img-src 'self' data: blob: · connect-src 'self'
frame-ancestors 'self'
```

**Nonce-bypass hardening (added 2026-07-28).** `object-src`, `base-uri` and
`form-action` were **absent entirely** — a gap the external audit did not
report, found by the CSP ratchet tests described below:

| Directive | Why it matters |
|---|---|
| `base-uri 'self'` | An injected `<base href="//attacker">` re-roots every **relative** script/style URL, turning a `'self'` + nonce policy against itself. The most serious of the three. |
| `object-src 'none'` | `<object>`/`<embed>` can execute active content that `script-src` does **not** cover. |
| `form-action 'self'` | Stops an injected or hijacked `<form>` POSTing credentials / CSRF tokens to a third-party origin. |

`script-src` has **no** `unsafe-inline`, `unsafe-eval` or `unsafe-hashes`.
Inline handlers work via the nonced, eval-free `csp_rebinder.js` (with a
`MutationObserver` for dynamically-added nodes), proven eval-free by
`tests/test_csp_rebinder.py`.

Residual exposure is `style-src-attr` only, and only on the **shells** —
runtime-computed `style="…"` attributes written by `safe_dom.js`. The standalone
document routes carry no style exception at all; see §7.3.1.

> **✅ DECISION (2026-07-28): ACCEPTED — this finding is closed.**
>
> Not accepted on argument, but on measurement. All three attack paths were
> driven in a real browser (Playwright) against the running app:
>
> | Attack | Result |
> |---|---|
> | `style="width: expression(...)"` executing script | **did not run** — legacy IE `expression()` is dead in modern engines |
> | Injecting a `<style>` element | **BLOCKED** by strict `style-src-elem` |
> | Injecting an inline `<script>` | **BLOCKED** by the `script-src` nonce |
>
> A style **attribute** cannot execute script, so the worst case is UI
> redressing, further constrained by `frame-ancestors 'self'`.
>
> **Why not refactor anyway:** it would mean rewriting ~36 inline `style="…"`
> attributes, several legitimately dynamic (`width:${pct}%`,
> `background:${color}`), and **all of them in the Jinja templates** — the
> *non-default* frontend, since `USE_SPA` defaults to `True` and ships the React
> SPA. That is real regression risk in exchange for no security gain.
>
> **What is guarded instead:** `tests/test_csp_policy.py` (5 tests) is a ratchet
> that fails the build if `script-src` loses its nonce or gains
> `unsafe-inline`/`unsafe-eval`, if `style-src-elem` weakens, or if
> `unsafe-inline` spreads to any directive beyond the accepted exception. The
> decision is enforced by CI, not by memory.

### 7.3.1 Zero-exception CSP for standalone documents (2026-08-04)

The 2026-07-28 decision above stands for the **shells** (Jinja and SPA): they
still carry `style-src-attr 'unsafe-inline'`, and they still need it, because
`safe_dom.js` calls `setAttribute('style', …)` on nodes it builds at runtime.

The **standalone document renders** are a different case. They are
server-rendered once, in full, with no runtime DOM building — so their style
attributes can be removed at render time. Four routes now do exactly that and
run with **no style exception at all**:

| Route / renderer | What it renders |
|---|---|
| `app/services/letterhead_renderer.py` → `_wrap_document` | 12 letterhead / undertaking documents |
| `app/services/receipts_renderer.py` → `_wrap` | receipts |
| `app/api/endpoints/documents.py` → `print_document` | designer print preview |
| `app/api/endpoints/candidates.py` → `print_candidate_profile` | candidate profile print |

**Why hoisting, not a policy edit.** CSP has no nonce mechanism for style
attributes — a nonce attaches to an *element*, and `style="…"` is not one. So
`'unsafe-inline'` cannot be replaced by a nonce; it can only be *deleted*, which
means the attributes themselves have to go. `app/core/style_hoist.py` walks the
finished HTML, moves each `style="…"` into a nonced `<style>` element, and leaves
behind a `data-csp-h="hN"` hook:

```html
<!-- before -->
<div class="field" style="left:12mm;top:40mm">

<!-- after -->
<div class="field" data-csp-h="h3">
<style nonce="…">[data-csp-h="h3"][data-csp-h]{left:12mm;top:40mm}</style>
```

**Cascade fidelity.** A style attribute beats every selector; a rule does not.
The generated selector is therefore **doubled** — `[data-csp-h="h3"][data-csp-h]`
— giving specificity **(0,2,0)**, enough to outrank the class rules in the
document stylesheets while staying below `!important`. That boundary is
deliberate: the print stylesheets use `!important` overrides, and those must keep
winning exactly as they did before. The design was checked against the real
letterhead and designer CSS: neither uses ID selectors, so nothing in the
documents can reach (1,0,0) and lose to the hook.

**Verified in a browser, not on paper.**

| Check | Result |
|---|---|
| Computed-style equivalence, original vs hoisted (Chromium) | `e_barcode` 16 elements — **0** property diffs, **0** geometry diffs; `undertaking_b` 20 elements — **0** / **0** |
| Live routes under the enforced `style-src-attr 'none'` header | `candidate_profile`, `protector_main`, `undertaking_b`, `designer_print` — **0** CSP violations each, **0** server-rendered style attributes left, hoisted rules present in the CSSOM (7 / 7 / 14), absolutely-positioned overlay fields still `position: absolute` (10 on `designer_print`) |

**What this does *not* cover, and why that is fine.** `designer_print` still ends
up with one live `style` attribute in the DOM: `style="--fit-scale: 1;"`, written
by `body.style.setProperty()`. It produced **zero** CSP violations. CSSOM writes
are exempt from `style-src-attr` — the directive governs *parsing* a style
attribute, not the property-level API. This was measured, not assumed, and it is
the reason the hoister only needs to handle server-rendered markup.

**Two implementation traps, both now pinned by tests.**

1. Segmenting the document with a regex was **unsafe**. A literal
   `</style><script>alert(1)</script>` sitting inside *another attribute's value*
   matched the protected-region pattern and forged a segment boundary, so the
   real style attribute in that tag was never sanitised and `alert(1)` survived.
   Replaced with a quote-aware scanner that only ever sees genuine tag and
   raw-text-element boundaries.
2. Splitting declarations on `;` corrupted **every** document background:
   `background-image:url('data:image/png;base64,…')` was cut in half. The
   splitter is now quote- and paren-aware and splits on top-level `;` only. No
   test covered this; it was found by reading the code, and it would have
   rendered every background blank.

Declarations containing `<`, `{`, `}` or `@` are dropped rather than escaped: a
`<style>` body is a raw-text element and ends at the first `</style`, *even
inside a CSS string literal*, so there is no encoding that makes those
characters safe there.

**Mutation-verified.** The middleware signal crosses a `BaseHTTPMiddleware`
boundary, where Starlette runs the downstream app in a **child** `Context` — a
plain `ContextVar.set()` from a route is invisible to the wrapping middleware,
while mutating a dict the middleware already holds does cross. That was
established by probe, and the guard was then confirmed by replacing the mutable
container with the naive `set()` version: both integration tests failed, as they
must. `tests/test_bg_fit.py` was likewise re-verified against the original
stretch bug after being taught to read the hoisted rule.

### 7.4 Authentication hardening

- **JWT in an httpOnly cookie** — not readable by JavaScript, so XSS cannot
  exfiltrate the session. The token is echoed in the response body **only** when
  `TESTING=true`, and production refuses to boot with that flag set.
- **bcrypt** password hashing (passlib).
- **CSRF** double-submit: a non-HttpOnly `csrf_token` cookie must be echoed in
  the `X-CSRF-Token` header.
- **Account lockout** and IP throttling on repeated failures.
- **Forced password change** on first login (`must_change_password`).
- **12-character minimum** password policy, applied consistently to reset and
  change flows.
- `X-Forwarded-For` handling is **not** naively trusted — the client IP is
  derived from `TRUSTED_PROXY_COUNT`, counting from the right of the XFF list.
  The earlier leftmost-entry approach let a client forge a fresh lockout bucket
  per request and defeat throttling entirely.

### 7.5 Account enumeration on password reset (found in-house)

`/api/auth/forgot-password` used to raise **500** when the SMTP send threw. That
path is reachable only *after* matching an active user, so the status code alone
disclosed registration:

```
registered address    -> send attempted -> throws -> 500
unregistered address  -> early return             -> 200
```

Likely live rather than theoretical: `.env.example` ships **placeholder** SMTP
values that are non-empty, so a naive truthiness check treated email as
configured, a real send was attempted, and authentication failed. Any deployment
that copied the example without configuring SMTP sat in the leaking branch.

**Fixed on both axes.** A delivery failure is a server-side fault that says
nothing about the address typed, so every branch now returns the same
account-neutral `200`, with escalation to the operator via ERROR log,
`/api/health` and a boot warning. Separately, `settings.email_configured` is now
the single source of truth for "can this server send mail?" and **rejects the
placeholders**, so a placeholder config yields the honest, symmetric `503`
up-front. Mutation-verified: the regression test was confirmed to fail against
the old code.

### 7.6 Other hardening in place

- **Path-traversal** protection on PDF background and upload paths.
- **Audit logging** of security-relevant mutations.
- **Structured JSON logging** with request-ID correlation.
- **Secret-safe release packaging** — two builders, each ending in a self-audit
  that **hard-fails** the build if anything forbidden slips in:
  - `scripts/make_release.sh` (recommended) — ships a **fresh single-commit git
    repository**, so the customer gets version control without inheriting the
    internal development history. Exports via `git archive`, which emits *only
    tracked* files, so secrets, live databases, virtualenvs and caches cannot
    leak by construction rather than by an exclude list. Also guards against
    the legacy vendor credential reappearing and against dangling doc links.
  - `scripts/make_release_zip.sh` — a bare source drop with **no** `.git` at all.
- **Reset tokens are never logged** at any level — they are hash-stored,
  single-use and 30-minute-expiry.
- **Production-readiness guard** (`Settings.assert_production_safe`) refuses to
  boot on a placeholder/short `SECRET_KEY`, a wildcard or empty `ALLOWED_HOSTS`,
  or `TESTING=true` in production. In development it auto-generates an ephemeral
  key and warns, so a fresh clone still boots.

### 8.1 The tenant storage boundary — how it can silently break (2026-08-15)

Tenant isolation in this portal is *physical*: every tenant gets its own
database (a SQLite file by default, a dedicated Postgres database when
`TENANT_DB_URL_TEMPLATE` is set). That design is only as strong as the code
that decides **which file to open**, and three defects were found there
during an audit triggered by a field report of a "missing MySQLdb module"
breaking backend startup.

The MySQL claim itself was **false** — there is no MySQL code path anywhere
in this codebase, and `DATABASE_URL` is `sqlite:///./data/dogar_trading.db`.
But chasing it surfaced three genuine bugs.

**Finding 1 (High) — the engine bypassed the single source of truth.**
`tenant_db_url()` documents itself as "the ONLY place URL construction
happens" and carries the project-root anchoring for the CWD-relative values
stored in `tenants.db_path`. But `_make_tenant_sessionmaker()` built its
SQLite URL inline as `f"sqlite:///{db_path}"`, so the anchoring was real yet
**unreachable by the engine**. Measured from `/tmp`:

| | resolved path |
|---|---|
| `tenant_db_url("acme", "data/tenants/tenant_acme.db")` | `sqlite:////home/user/webapp/data/tenants/tenant_acme.db` |
| engine actually bound to | `sqlite:///data/tenants/tenant_acme.db` |

The failure mode is the dangerous kind: **SQLite creates a missing file
instead of erroring.** Launched from any directory other than the project
root (systemd `WorkingDirectory=/`, a Docker entrypoint that `cd`s, cron),
each tenant silently received a brand-new *empty* database. The operator sees
a portal that logs in perfectly and shows zero records — no error, no log
line, no crash.

**Finding 2 (High) — the "is the tenant DB missing?" guard tested a different
path than the engine opened.** `_row_to_resolved()` called
`os.path.exists(row.db_path)` on the raw relative value while the engine
anchored to the project root. From a foreign CWD the two disagreed, so a
tenant whose database exists was reported missing — and because a missing
tenant DB is deliberately a hard 503 (it must never fall back to the control
DB), the entire tenant surface went down.

**Finding 3 (Medium) — the unsupported-scheme path lied twice.** The fallback
branch in `app/db/session.py` carried the comment *"let SQLAlchemy raise a
clear error at first connect"*. Both halves were wrong. `create_engine()`
imports the DBAPI **eagerly**, so an unsupported scheme dies at *module
import* — during startup, before any route exists. And the error was:

```
ModuleNotFoundError: No module named 'MySQLdb'
  … sqlalchemy/dialects/mysql/mysqldb.py:147 in import_dbapi
```

Nothing in that traceback names `DATABASE_URL`, the portal, or the fact that
MySQL is not a supported backend. **This is precisely how the false field
report was generated**: the traceback reads as a missing OS package, so the
rational next step is `apt install python3-mysqldb` — which cannot help,
because the application has no MySQL code path to run.

**Fixes.** The SQLite branch of `_make_tenant_sessionmaker` now routes
through `tenant_db_url()`, making the single-source-of-truth claim true for
both backends; the existence check anchors through the same helper; and an
unsupported scheme now raises a `RuntimeError` naming the offending scheme,
the two supported backends, and explicitly warning that installing a driver
will not help.

**Verification.** Five behavioural tests in `tests/test_tenancy.py` §3 assert
on observable behaviour only — the URL the engine is bound to, whether a
stray file appears on disk, and the message actually raised — never on source
text. Three mutations reverting each fix were run; **3/3 were caught**, and
the third reproduced the exact `ModuleNotFoundError: No module named
'MySQLdb'` from the field report, proving the test guards that specific
failure. A positive test pins that `sqlite://` and `postgresql://` still
build an engine, so a guard that rejected everything could not pass.

### 8.2 Tenant data isolation — measured, not asserted (2026-08-15)

The requirement is that each recruitment office is its own isolated tenant
with a *strictly separate* data boundary, and that the Dogar portal and its
migrated records remain **only** the Dogar tenant, never shared or mixed.
That is a claim about behaviour, so it was measured.

**Physical separation (live workspace).**

| database | candidates | users |
|---|---|---|
| `data/dogar_trading.db` (control / Dogar) | 2,675 | 5 |
| `data/tenants/tenant_acme.db` | 0 | 1 |
| `data/tenants/tenant_beta.db` | 0 | 1 |

Every migrated Dogar record lives in the Dogar database and appears in no
other tenant. Each provisioned tenant gets its own file and its own seeded
admin user.

**The routing invariant.** Physical separation is only preserved if every
request resolves to the right file. A route that declares
`Depends(get_db)` talks to the CONTROL database regardless of which tenant
host the request arrived on — so a tenant user hitting it would read and
write Dogar's records. An audit of all 167 routes found:

* **134** business endpoints correctly on `Depends(get_tenant_db)`
* **13** on `Depends(get_db)`, all in `app/api/endpoints/tenants.py` — the
  tenant registry, which lives in the control DB by definition
* **0** business endpoints leaking to the control DB

**Why this needs a permanent guard.** This class of leak is *invisible* in
single-tenant testing: on the root host `get_tenant_db` transparently yields
the control DB, so a mis-wired route behaves identically until the day a
second tenant exists. `test_no_business_endpoint_is_bound_to_the_control_database`
therefore asserts the wiring structurally and fails the moment anyone adds
`Depends(get_db)` to a business route. Mutation-verified: injecting
`Depends(get_db)` into a candidates route was **CAUGHT**.

**Identity isolation.** Tokens carry a `tnt` claim (the tenant slug, `""` for
root). `get_current_user_optional` rejects a token whose claim does not match
the tenant the request resolved to, so a token minted for tenant A cannot
authenticate against the root portal or tenant B — which matters because the
same numeric user id belongs to a different person in each database.

**Branding and features** are per-tenant columns on the `tenants` row (name,
short name, subtitle, primary colour, logo, letterhead, licence number,
office address, receipt template, demand format) plus a `features` JSON map
of 15 toggleable capabilities. Dogar's own branding is untouched by tenancy:
the root host resolves to no tenant and renders exactly as before.

### 8.3 The document audit trail — what was missing (2026-08-15)

**Operator requirement:** *"an admin audit log that records login history and
every role-protected document action (view/edit/print/disable) with timestamps
and user IDs in real time."*

**Login history** already satisfied its half: every attempt, Success and
Failed alike, has been written to `login_history` with IP and user-agent
(454 rows on the live database), and `GET /api/users/login-history` already
exposed it.

**Document actions satisfied none of it.** Measured before the change:

```sql
sqlite> select count(*) from audit_logs where entity_type='document';
0
```

`app/api/endpoints/documents.py` — 19 routes, ~2350 lines — contained no audit
call at all. The two most sensitive operations were the least traceable:

| Route | Why it was invisible |
|---|---|
| `GET /templates/{id}/print` | Renders the HTML print view. No file is downloaded, so the `GeneratedDocument` bookkeeping row is never written either. **The most common way a document was actually printed left no trace anywhere.** |
| `GET /templates/{id}/preview-data` | Merges **real** record values into the overlay. Reading a candidate's passport or CNIC through it is a disclosure event, and it was equally invisible. |

`GeneratedDocument` is not a substitute: it is document-management
bookkeeping (no actor IP, no user-agent, not queried by any audit viewer) and
it only exists for the PDF path.

**What was built.** `AuditAction` gained `VIEW`, `PRINT`, `DISABLE`, `ENABLE`;
`app/services/audit.py` gained `log_document_action()`; six handlers were
wired (`get_template`, `update_template`, `delete_template`, `preview_data`,
`generate`, `print_document`). Toggling `is_active` records **enable/disable**
rather than a generic update, so the operator can filter for exactly the
action they named. `occurred_at` is a server-side `func.now()` default, so the
timestamp is the database's and a caller cannot backdate its own trail.

**The viewer came back.** An audit-log viewer had existed and was deleted on
2026-07-30, together with the `audit:view` permission — correct at the time,
since a checkbox granting access to nothing is a lie to the operator. Both are
restored: `GET /api/users/audit-log` (filterable by entity type, action,
actor, date range, summary text) plus `GET /api/users/audit-log/_meta/filters`,
which populates the dropdowns from the data so a newly-audited action appears
without a frontend change. Both read `get_tenant_db`, so one office can never
read another office's trail.

**Two defects were found by the tests, not by inspection.**

1. *Best-effort auditing was not actually best-effort.* `log_event` wraps only
   the `db.add`/`db.commit`. It does not protect the caller from the argument
   construction that happens *before* the call — a detached SQLAlchemy
   instance after a rollback is the realistic case. With the logging stack
   made to raise, the print endpoint returned **500**. An observability
   feature that introduces a new way for printing to fail is worse than the
   missing log line, so `log_document_action` now carries its own outer guard.

2. *RBAC drift was only detected in one direction.* The suite already failed
   on a catalogue key that no code enforces. Nothing caught the **reverse**: a
   key a route enforces that the catalogue never declares. That direction is
   not harmless — the Roles editor renders its checkboxes from
   `PERMISSION_CATALOG`, so an undeclared key is a capability **no custom role
   can ever be granted**, while admins still pass through the `"*"` wildcard
   and the route looks fine in testing. Deleting `audit:view` from the
   catalogue left the whole suite green (mutation GI). Guarded now by
   `test_every_enforced_permission_is_declared_in_the_catalogue`.

**Verification.** `tests/test_audit_trail.py` — 16 tests, exercising the real
HTTP stack. Nine mutations were applied; all nine turn the suite red:

| GB | Remove the UPDATE/DISABLE audit in `update_template` | CAUGHT |
| GC | Remove the PRINT audit in `print_document` | CAUGHT |

### 8.4 Per-capability document route guards (2026-08-15)

**Operator requirement:** *"Verify and harden role-based access by enforcing
route guards for view, edit, disable, and print actions per document type,
returning a clear 403/redirect when I lack permission."*

**Audit result: all 19 document routes were already guarded**, and with the
correct capability in each case — `documents:view` on the seven reads,
`documents:edit` on the seven writes, `documents:designer` on the two
destructive bulk operations, `documents:print` on `generate` and
`print_document`. Nothing was open. That was worth *verifying* rather than
asserting, because the previous whole-app audit had already produced one
false negative: a decorator-only scan reported `tenants.py` as unguarded when
in fact 13 of its 14 routes call `_admin_only()` in the body.

**Why a new test module was still needed.**
`tests/test_rbac_enforcement.py` answers *"is this key enforced anywhere?"* —
a corpus grep plus a few escalation probes. It cannot answer the question the
operator actually asked, which is per-route and per-capability. All four
document keys resolve through the same `require_permission` factory, so
guarding an *edit* route with `documents:view` is a one-word slip that leaves
both keys "enforced somewhere" and the corpus grep perfectly green — while
any user who can look at a template can now rewrite it.

`tests/test_document_route_guards.py` (40 cases) probes the full matrix:

| Subject | Holds | Purpose |
|---|---|---|
| custom role, **empty** permission list | nothing | every route must 403 |
| `staff` | `documents:view`, `documents:print` | must still be refused edit + designer |
| `manager` | all four document keys | positive control — the guards must still *admit* |

The zero-permission subject is the one that makes the matrix honest. Staff
legitimately holds view and print, so a suite built on Staff alone could
never test those two capabilities — it would pass them by entitlement. The
custom role is a real persisted `Role` row with `permissions = []`, which is
what an operator creates in the Roles editor when they revoke everything, and
it exercises the `_parse_perms` path rather than the `ROLE_PRESETS` fallback.

**Refusals are asserted to be exactly 403** — never 401, never 500. A 401
tells the SPA "your session expired" and bounces the user to the login
screen; they would sign in again, succeed, land back on the same refusal, and
never learn that the real answer is "your role does not allow this". A 500
means the guard itself crashed, which is not a guard.

**Disable** has no route of its own — it is `PUT {"is_active": false}` — so it
is only as protected as that PUT. The test asserts both the 403 *and* that
the template was not actually disabled, so a guard that ran after the
mutation would be caught. It is asserted explicitly so that if the toggle is
ever split onto its own endpoint, the guard has to be decided again rather
than defaulting to open.

**Verification.** Six mutations, all caught:

| # | Mutation | Result |
|---|---|---|
| HA | `update_template` guarded by `documents:view` | CAUGHT |
| HB | `delete_template` guarded by `documents:view` | CAUGHT |
| HC | `create_template` loses its guard (plain auth) | CAUGHT |
| HD | `print_document` loses its guard (plain auth) | CAUGHT |
| HE | `dedupe_all_fields` guarded by `documents:view` | CAUGHT |
| HF | `bulk_save_fields` loses its guard (plain auth) | CAUGHT |

A structural test also fails if any *future* route is added to
`documents.py` without a `require_permission` / `assert_permission` in its
signature — the matrix can only probe routes it already knows about.

### 8.5 Per-tenant feature sets — enforced, not just stored (2026-08-16)

**The finding.** Every tenant row carried a `features` JSON map, Portal Admin
rendered checkboxes for it, and `PUT /api/tenants/{id}/features` saved it. But
nothing ever *read* it. `ResolvedTenant` — the snapshot the middleware attaches
to each request — had no `features` field at all, so no request handler could
consult one. A tenant provisioned with `ai_ocr: false` still had complete OCR
access; the operator's own admin screen told them a capability was off while
the API served it. The feature set was decorative.

**What was built.**

| Layer | Change |
|---|---|
| `ResolvedTenant` | new `features` mapping, populated in `_row_to_resolved` |
| `tenant_feature_enabled(request, feature)` | reads the snapshot; unknown flags and the root portal answer `True` |
| `require_tenant_feature(feature)` | FastAPI dependency, raises **404** when disabled |
| `app/main.py` | router-level gates on `/api/ocr`, `/api/v1/documents` (OCR validation) and `/api/chatbot` |
| `GET /api/tenants/_meta/current` | now returns the merged feature map so the SPA and the server agree |

**404, not 403.** A 403 says "this exists and you may not use it", which tells
one recruitment office that another office bought a capability they did not.
A disabled feature is made indistinguishable from one that was never installed.

**Router-level, not per-route.** These are whole capabilities. Gating six of a
router's seven routes leaves a hole, and the next route added to that router
would be unprotected by default. The dependency sits on `include_router`, so
coverage is automatic.

**Unknown flags fail open, deliberately.** A tenant row written before a flag
existed simply lacks the key. Treating "absent" as "disabled" would silently
switch off working features for existing offices during an upgrade. Absent
means enabled, and `_meta/current` merges over `Tenant.default_features()` so
the client reaches the same conclusion the server does.

**Verification** — `tests/test_tenant_isolation_live.py`, 12 tests using real
provisioned tenants over the `/t/<slug>/` path mode: cross-tenant data
isolation in both directions, `tnt` token-claim rejection, disabled feature
refused server-side, 404-not-403, enabled feature still served, the root portal
never gated, per-tenant branding, and root Dogar branding unchanged.

| # | Mutation | Result |
|---|---|---|
| IA | feature gate always allows (the pre-fix world) | CAUGHT |
| IB | features dropped from the request snapshot | CAUGHT |
| IC | disabled feature answers 403 instead of 404 | CAUGHT |
| ID | the OCR router loses its gate | CAUGHT |
| IE | the chatbot router loses its gate | CAUGHT |

### 8.6 The mutation harness was unsound — a stale-bytecode trap (2026-08-16)

This section exists because the evidence in §8.3–§8.5 was, for a time, **not
trustworthy**, and the failure mode is subtle enough to be worth recording.

**Symptom.** Two tenancy tests passed alone and failed in the full suite. The
application returned `403` where `app/core/tenancy.py` plainly said
`status_code=404`. `inspect.getsource` agreed with the file. A minimal FastAPI
reproduction confirmed the framework does not rewrite a router dependency's
404. The running code and the source code disagreed.

**Cause.** CPython validates a cached `__pycache__/*.pyc` by comparing
*(integer-second mtime, byte size)* against the source — not a hash. The
throwaway mutation script used `shutil.copy` to back the file up (which does
**not** preserve mtime) and `shutil.move` to restore it, and the mutation in
question was `404` → `403`: **exactly the same byte length**. After the
restore, both validation fields matched the *mutant's* cached bytecode, so
Python kept executing the mutant while the file on disk was correct. The cache
outlived the script and poisoned ordinary test runs.

**Consequences, both real.** A poisoned cache can also make a *later* mutation
report a false CAUGHT. Every mutation result produced by the old scripts was
therefore discarded and re-earned.

**The fix** — `scripts/mutation_check.py`, now a permanent, reviewable tool:

* subprocesses run with `PYTHONDONTWRITEBYTECODE=1` and `-B`, so a mutant can
  never be cached at all;
* `__pycache__` is purged before the run and after every mutation;
* restore is byte-exact from an in-memory copy, is re-read and compared, and
  bumps the file's mtime to invalidate any surviving cache;
* a **green baseline is required** before mutating — otherwise "CAUGHT" only
  means the suite was already red;
* anchors must be **unique**; a non-unique anchor is reported `AMBIGUOUS`
  rather than silently mutating the first match. This immediately caught a
  second flaw: `status_code=404,` matches twice in `tenancy.py`, so the old
  script had been mutating tenant *resolution*, not the feature gate;
* `mode="all"` mutates **every** occurrence, for protections applied at many
  call sites. This matters for honesty: mutating one of six audit call sites,
  or one of eight `documents:edit` guards, proves one site is covered while
  implying all of them are.

Re-earned under the corrected harness: tenancy **5/5**, audit **5/5** (GA now
across all 6 handlers), document guards **3/3** (across 8 + 2 + 2 sites).

```bash
./venv/bin/python scripts/mutation_check.py all
```

### 9.2 Authentication flow

```bash
# 1) GET any page to obtain the CSRF cookie
curl -c jar.txt https://portal.example.com/login -o /dev/null

# 2) Extract csrf_token and log in (JWT is set as an httpOnly cookie)
CSRF=$(grep csrf_token jar.txt | awk '{print $7}')
curl -b jar.txt -c jar.txt -X POST https://portal.example.com/api/auth/login \
     -H "Content-Type: application/json" \
     -H "X-CSRF-Token: $CSRF" \
     -d '{"email":"admin@example.com","password":"…"}'

# 3) Subsequent calls reuse the cookie jar + CSRF header
curl -b jar.txt https://portal.example.com/api/clients/
```

> Note trailing slashes on collection routes (`/api/clients/`). Without one you

> is supplied.

| Module | Guards |
|---|---|

### 14.3 The CSS containing-block trap (dialogs clipped mid-form)

Reported with screenshots: the **Customize Role** dialog rendered cut off
mid-form — Role Name and Description visible, everything below them gone, and
**Save Changes unreachable**. The page behind appeared to end at the same hard
horizontal line. **Provision New Portal** had the identical defect. Both were
completely unusable.

**Root cause.** `position: fixed` does not always resolve against the viewport.
It resolves against the nearest ancestor that establishes a *containing block*,
which any non-`none` `transform`, `filter`, `backdrop-filter`, `perspective`,
`contain` or `will-change` creates. The routed page content is wrapped in
`.page-enter`, whose route-transition animation was declared:

```css
animation: page-enter 140ms cubic-bezier(...) both;  /* `both` */
will-change: opacity, transform;                     /* never released */
```

`animation-fill-mode: both` keeps the keyframe transform asserted **after the
animation ends**, and a statically declared `will-change` is **never released**.
That wrapper was therefore a containing block for the entire lifetime of the
page, so any `fixed inset-0` overlay left inside the routed tree was sized and
clipped to the content wrapper instead of the viewport.

Measured in Chromium at 1024×640, before and after neutralising `will-change`
on the wrapper:

| | overlay size | overlay origin | viewport |
|---|---|---|---|
| before | 736 × 180 | (264, 151) | 1024 × 640 |
| after | 1024 × 620 | (0, 20) | 1024 × 640 |

**Why only two dialogs broke.** Four of the six hand-rolled `fixed inset-0`
overlays were already portalled to `<body>` (including the shared `<Modal>` in
`components/ui.tsx`, and the Topbar modals, which had to escape the header's
`backdrop-blur` for exactly this reason). The CSS bug was latent app-wide but
could only bite the two overlays that were still rendered inside the page tree:
`MiscPages.tsx` Roles (:196) and Provision (:750).

**Fix, in two layers.**

1. **Cause** — `.page-enter` now uses `forwards` (the final keyframe is
   `transform: none`) and declares no `will-change`. The wrapper stops being a
   containing block at all.
2. **Immunity** — both dialogs are now wrapped in
   `createPortal(…, document.body)`, so no future ancestor `transform`/`filter`
   can ever clip them again, plus a viewport-relative `max-h-[calc(100vh-…)]`.

`tests/test_fixed_overlay_containing_block.py` fails if `both` or
`will-change` returns to `.page-enter`, or if any `.tsx` file gains a
`fixed inset-0` overlay without a matching `createPortal` call.

**Found while verifying the fix (not reported by anyone).** A browser sweep of
every reachable dialog at 1024×640 measured two more whose action bars sat
**below the fold**: *Create Demand File* step 1 (775 px of content inside a
608 px card) and *Edit Demand File*. These were **not** clipped — the card
scrolls, so they were reachable and merely poor. They are reported separately
from the clipped pair on purpose: conflating "unreachable" with "needs a
scroll" would have meant claiming defects that did not exist. Both now use the
new `.spa-modal-foot` utility, the sticky counterpart to the already-sticky
`.spa-modal-head`.

### Suppressing an XSS finding

Prefer escaping. If a value genuinely holds pre-built trusted markup, add a
per-line `xss-sink-ok` pragma with a justification, or a reviewed entry in
`TRUSTED_MARKUP_VARS_BY_FILE`. The pragma is **greppable by design**, so waivers
cannot quietly accumulate.

### 14.4 Credential hygiene: why a green suite missed a committed password

On 2026-08-13 the bootstrap admin password was found in **two tracked files**:

| Location | Form |
|---|---|
| `scripts/ui_verify.mjs:89,90` | hardcoded as the 4th argument to `checkPortal()` |
| `FULL_AUDIT_REPORT_2026-08-05.md:301,302` | printed verbatim in a `.env` configuration table (admin **and** vendor) |

The suite was at 681 passing tests, ruff was clean, the XSS ratchet reported 0
sinks, and the coordinate engine passed at 0.02 pt. None of that was relevant:
**no test looked at credentials**, so a live production password sitting in
version control was invisible to the entire stack. This is the general lesson —
a green suite is evidence of what you chose to assert, nothing more.

#### What the app's auth state actually is (and why SECRET_KEY had to rotate)

Before deciding what to revoke, the auth layer was read rather than assumed:

* `app/api/endpoints/auth.py::login` issues **one** browser credential: the
  HttpOnly `access_token` cookie.
* That cookie is a **stateless JWT** signed with `SECRET_KEY`
  (`app/core/security.py::create_access_token`). Payload is `{sub, exp, tenant}`.
* There is **no session table, no refresh-token table, no remember-me token and
  no JWT denylist.** `logout` only calls `delete_cookie`, which is a client-side
  hint.
* The only server-side auth artefact is `password_reset_tokens`
  (`app/models/lookups.py`), storing SHA-256 hashes of one-time reset links.

The consequence is counter-intuitive and worth stating plainly: **changing the
password does not log anybody out.** A stolen `access_token` keeps working until
`exp`. Therefore rotating `SECRET_KEY` *is* this application's
session-revocation lever — every previously issued token fails signature
verification immediately. Any credential rotation performed in response to a
suspected compromise must rotate `SECRET_KEY` too, or it is incomplete.

#### The remediation

1. Literals removed from both files. `ui_verify.mjs` now resolves credentials
   from `$ADMIN_EMAIL` / `$ADMIN_PW`, falling back to parsing `.env`, and
   **exits 2 with an explanatory message when neither is present** — it fails
   closed rather than guessing.
2. Both accounts rotated with `scripts/rotate_bootstrap_passwords.py`, which
   uses the app's own `User` model and `hash_password()` rather than raw SQL, so
   the stored hash format cannot drift from what `verify_password()` expects.
   New values are 43-char `secrets.token_urlsafe(32)`.
3. `SECRET_KEY` rotated in the same run; the one outstanding
   `password_reset_tokens` row was revoked.
4. Verified against the running service, not asserted:

   | Check | Result |
   |---|---|
   | old admin password → `POST /api/auth/login` | **401** (was 200 before) |
   | new admin password → `POST /api/auth/login` | **200** |
   | pre-rotation `access_token` cookie → `/api/users/me` | **401** (session revoked) |
   | old vendor password | **401** |
   | new vendor password | **200** |
   | new secret present anywhere but `.env` | **no** (tree, bundle, PM2 logs all clean) |

#### The rotation script no longer prints secrets

The original version printed both new passwords to stdout. Under PM2, Docker or
CI **stdout is a log file**, so every "rotation" wrote a fresh copy of the new
credential into a place nobody thinks to scrub. It now writes to `.env`
(chmod 0600, gitignored) and prints only a 12-hex-char SHA-256 fingerprint, so
an operator can confirm *which* value landed without the value itself entering a
log. `--print-admin-password` remains for an interactive, unlogged terminal.

#### A bug the behavioural test found

`_revoke_reset_tokens()` originally wrapped its query in
`except Exception: db.rollback(); return 0`. On any database **without** the
`password_reset_tokens` table (a fresh install before migrations), that rollback
discarded the caller's still-pending password change — `rotate()` reported
"verification FAILED" and left the compromised password live. **A rotation that
silently does nothing is worse than no rotation, because the operator believes
they are safe.** The table's presence is now probed with the SQLAlchemy
inspector *before* any query, so the transaction is never poisoned. Structural
grep tests could never have found this; the test that did runs the real
`rotate()` against a throwaway DB containing only the `users` table.

#### The permanent ratchet

`scripts/scan_committed_secrets.py` (`--check` in CI, wrapped by
`tests/test_no_committed_secrets.py`) applies three rules:

1. **Known-compromised literals** — the burned strings, banned everywhere
   including `.env`. Stored *split* in both the scanner and the test so neither
   file contains the literal it bans.
2. **Live `.env` secret values** — every value of a `*PASSWORD` / `SECRET*` /
   `*_KEY` / `*TOKEN` key is searched for across the tree. This is the
   generalised guard: it protects secrets that **do not exist yet**, which a
   fixed literal list cannot.
3. **Generic `password = "literal"` assignments** in source.

`app/static/spa/assets` is scanned **on purpose** — a secret compiled into the
browser bundle is served to every visitor, which is strictly worse than one in a
source file. `test_the_scanner_scans_the_built_bundle_directory` fails if
`SKIP_DIRS` ever grows to exclude it.

Rule 3 was tuned once: its first draft flagged
`errs.password = 'Password is required.'` in `Login.tsx` — six false positives
across four files. **A noisy ratchet earns a blanket suppression and then
protects nothing**, so values containing whitespace are now excluded (a
credential is one opaque token; UI prose is several words). The trade-off is
stated in the source: a hardcoded *passphrase with spaces* would slip past rule
3, but rules 1 and 2 still cover it.

#### Mutation-verified

Eleven mutations were applied to the protections and the suite had to fail for
each (`/tmp/mut7/run.py`, **11/11 CAUGHT**): reintroduce the literal in
`ui_verify.mjs`; reprint it in the audit table; empty the compromised-literal
list; `if False:` around the `SECRET_KEY` write; invert that guard; skip the
password-hash write; skip token revocation; restore the fatal `db.rollback()`;
exclude the served bundle; print the password unguarded.

Two of those mutations exposed **vacuous tests of my own**:

* `assert "SECRET_KEY" in src` passed while the write was disabled with
  `if False:` — it asserted that the script *mentions* the constant, not that it
  *writes* it. Replaced with an AST check requiring the enclosing `if` test to
  be exactly `not keep_secret_key`.
* Nothing at all covered reset-token revocation, so replacing the query with
  `rows = []` changed nothing. Now covered by a test that seeds three tokens
  (unused / already-used / other user) and asserts unused rows are stamped while
  the already-consumed row's `used_at` is preserved for audit history.

**Do not put a credential in this repository, in any file, for any reason —
including as a convenient test fixture.** Record assessments (length, strength,
fingerprint), never values.

## 15. User Guide

### 15.1 First run

1. Sign in with the bootstrap admin credentials from `.env`.
2. Change the password when prompted (enforced).
3. **Settings → General** — company name, licence number, letterhead, logo.
   These appear on every generated document.
4. **Settings → Lookups** — embassies, visa categories, cities, medical centres.
5. **Users** — create real accounts and assign roles. Avoid sharing the admin
   account; the audit log is only meaningful with per-person accounts.

### 15.2 Day-to-day: employer request → deployed worker

**Step 1 — Register the client.** Clients → New. Enter company and sponsor
details, including **Arabic** sponsor name and address (required by Gulf
paperwork).

**Step 2 — Create the demand file.** Demands → New. Attach it to the client,
enter the government file number, and add one trade line per occupation with
headcount, salary and contract term.

**Step 3 — Add candidates.** Candidates → New opens the guided wizard.
Upload the passport scan first and let **OCR** pre-fill identity fields — then
**verify them**, since OCR is assistive, not authoritative. The wizard is
resumable: an interruption does not lose work.

**Step 4 — Assign to a trade.** From the demand file or the candidate profile.
The demand's fill counters update automatically.

**Step 5 — Advance through the workflow.** Move candidates through
`docs_pending → docs_complete → protector → medical → visa_stamping →
e_number → travel_ready → deployed`. Use the document checklist to track what
is still outstanding.

**Step 6 — Generate documents.** Documents → pick a template → generate for a
candidate or demand. Templates render onto a scanned background so output aligns
with pre-printed official forms.

**Step 7 — Track money.** Record sub-agent commissions in the cashbook, issue
receipts, and review client statements.

**Step 8 — Watch reminders.** The reminder panel surfaces expiring passports,
medicals and visas. Clear them deliberately rather than dismissing in bulk —
an expired medical discovered at the airport is expensive.

### 15.3 Document designer

Documents → Templates → select → Designer.

1. Upload a scan of the real form as the background.
2. Drag fields onto the canvas and bind each to a data field.
3. Set font, size and alignment per field.
4. Preview against a real candidate to confirm alignment before printing at
   volume.

### 15.4 Custom roles

Roles → New. Tick permissions from the 44-permission catalogue and assign the
role to users. Start from the closest preset and remove what is not needed —
granting broadly and trimming later tends not to happen.

## 16. Troubleshooting

| Symptom | Cause | Resolution |
|---|---|---|
| **Login says "Invalid username or password" with the password from `.env`** | `DEFAULT_ADMIN_PASSWORD` was changed *after* the admin row was first created. `seed_admin_user()` returns early when the admin already exists, so it never re-hashes the password — `.env` and the stored hash have drifted apart. **This is the single most common false "the app is broken" report.** | `./venv/bin/python scripts/reset_admin_password.py --email <admin-email> --password '<new>' --clear-must-change`. See §16.1 |
| **Login fails with a password like `Preview-xxxxxxxx`** | The browser autofilled the *sandbox/hosting preview* password into the portal form. That protects the URL, it is **not** a portal account. | Clear the field and type the portal password. Disable autofill for the site |
| **Editing a Jinja template changes nothing** | `USE_SPA=true` serves the React SPA | Set `USE_SPA=false` and restart, or edit the SPA source |
| **App refuses to start, `SECURITY BLOCKER`** | Production guard | Read the message — usually `SECRET_KEY`, `ALLOWED_HOSTS`, or `TESTING=true` |
| **Forgot-password returns 503** | SMTP unconfigured or placeholder values | Configure SMTP, or reset via admin / `reset_admin_password.py` |
| **Sessions drop on every restart** | Ephemeral dev `SECRET_KEY` | Set a stable `SECRET_KEY` in `.env` |
| **403 on POST/PUT/DELETE** | Missing CSRF header | GET a page first, then echo `csrf_token` in `X-CSRF-Token` |
| **307 on a POST to `/api/clients`** | Missing trailing slash | Use `/api/clients/` (or `curl -L`) |
| **Rate limiting hits everyone at once** | Proxy IP treated as the client | Set `TRUSTED_PROXY_COUNT` to the real proxy depth |
| **Arabic renders as disconnected letters** | `arabic-reshaper` not installed | `pip install arabic-reshaper` |
| **PDF text fails to render** | `libfreetype6` missing | Install the system package |
| **OCR returns nothing useful** | No `OPENAI_API_KEY`; MRZ/text fallback only | Add the key, or use a sharper, flatter scan |
| **Page loads but is completely inert** | JS `SyntaxError` aborted the script block | Open the browser console; check for redeclared globals (regression-tested) |
| **SSE status stream stalls behind nginx** | Response buffering | `proxy_buffering off;` on that location |

### 16.1 Locked out of the portal — the definitive fix

Nine times out of ten a "login is broken" report is one of the two causes in the
first rows of the table above, and neither is a fault in the auth code.

**Why the `.env` password can stop working.** The bootstrap admin is created by
`seed_admin_user()` in `app/db/init_db.py`. It hashes `DEFAULT_ADMIN_PASSWORD`
**only on the boot where it creates the row**. On every later start it finds the
row, prints `Admin already exists: …` and returns *without touching the
password*. So editing `DEFAULT_ADMIN_PASSWORD` in `.env` after first boot has no
effect on the database, and the login screen keeps rejecting the value you can
plainly see in the file.

That early return is **intentional, not a bug**: re-hashing on every boot would
silently overwrite whatever password an admin had chosen in the UI and would
resurrect the `.env` value forever. The behaviour is pinned by
`tests/test_auth.py::test_seed_admin_does_not_rewrite_an_existing_password`, so
it cannot change without someone updating this section.

**Recovery — the supported path:**

```bash
# See exactly which accounts exist, and their role / active / must-change flags
./venv/bin/python scripts/reset_admin_password.py --list

# Set a known password and clear the forced-change prompt
./venv/bin/python scripts/reset_admin_password.py \
    --email admin@yourcompany.com \
    --password 'YourStrongPassword_2026!' \
    --clear-must-change
```

The script re-hashes the password onto the existing row and verifies it before
exiting, so a successful run guarantees the next login attempt will succeed. It
is deliberately standalone — it needs no working login, which is the whole point
when you are locked out.

**After recovery, put the same value back in `.env`** so the file and the
database agree again. They are independent stores; nothing keeps them in sync
automatically.

> **Autofill warning.** If the portal is behind a hosting/sandbox preview
> password, browsers happily autofill *that* value (it often looks like
> `Preview-…`) into the portal's own password box. It will always fail: it
> protects the URL, it is not an account in this application. Clear the field
> and type the portal password.

## 18. Roadmap & Known Limitations

### Known limitations

| Area | Limitation |
|---|---|
| **CSP** | `style-src-attr 'unsafe-inline'` remains on the Jinja/SPA **shells**, which need runtime `setAttribute('style')`. Accepted on browser measurement (§7.3). The standalone document routes are exception-free (§7.3.1). |
| **Dual frontend** | Two UIs mean UI changes may need doing twice. A future release should retire one. |
| **Password reset** | Requires SMTP; otherwise admin-driven only. Fails closed by design. |
| **OCR accuracy** | Assistive, not authoritative. Always human-verified. Best AI results need `OPENAI_API_KEY`. |
| **SQLite concurrency** | Fine for a single agency; move to PostgreSQL for many concurrent writers. |
| **Alembic baseline** | A single baseline revision; older deployments should verify with `verify_postgres_parity.py`. |
| **Template page size vs artwork aspect** | Templates 1, 7 and 8 are Letter (612x792) while their scanned artwork is A4-proportioned (1653x2339 / 1624x2339), a 9.3–11.3% aspect mismatch absorbed by `bg_fit=fill`. **Accepted by owner instruction (2026-08-02): "Keep templates 1, 7, and 8 on Letter size unless a confirmed business requirement requires A4."** Do not run `scripts/fix_template_geometry.py` against them — it rescales geometry to the artwork aspect and would move every verified field. |
| **PDF field placement is per-form manual work** | Coordinates come from measuring the scanned artwork, not from any automatic layout. Adding or re-homing a field on a pre-printed government form requires measuring that form's printed rules. §4.14 documents the method and the two pitfalls that cost repeated passes. |
| **The OEP address comb physically cannot hold most addresses** | The pre-printed form has **two** address rows (rules measured at `y_pt` 397.0 / 416.5 / 436.0), giving a hard capacity of **26 characters**. **2,198 of 2,636 stored addresses (83.4 %) are longer** — median 35, 90th percentile 52, longest 91. The engine truncates at capacity and logs an overflow warning (`dtc.pdf_engine`). This is a property of the paper, not a defect: there is no third row to bind. Resolving it requires a **business decision** — an abbreviation policy at data entry, a smaller (less legible) cell pitch, or printing the address as free text outside the comb. See §4.10.1. |
| **`passport_issue_place` is collected but never filled** | The input exists (`AssignWizard.tsx:425`) and the backend stores it, but it is empty for all 2,675 candidates, so the OEP form prints a blank box. Nothing is broken — this needs an **operator process/training** fix, or the field should be unbound. Distinct from the `email` defect (no input at all), which was a code fault and was fixed 2026-08-12. See §4.10.2. |
| **No automated test renders the UI** | The suite asserts on *source text* for frontend concerns; nothing launches a browser, so no test can see a defect that only exists after the cascade is resolved. That is exactly how two dialogs shipped clipped and unusable (§14.3) with 656 tests green. The static guards added in `test_fixed_overlay_containing_block.py` pin the *known* causes (a containing-block-creating property on `.page-enter`; an un-portalled `fixed inset-0` overlay), which is cheap and catches regressions of this specific bug — but it is **not** a substitute for rendered-geometry checks. Closing this properly means a Playwright job in CI that opens every dialog at a small viewport and asserts each submit control is on screen. The measurement scripts used to diagnose and verify §14.3 do this and should be promoted out of `/tmp`. |
| **`test_portability.py` under memory pressure** | `test_app_imports_and_serves_from_an_unrelated_working_directory` spawns a real uvicorn subprocess with a 300 s timeout. On a constrained box (≈1 GB RAM) a full-suite run can exhaust memory and trip that timeout; it passes in ~7 s in isolation. Observed at 747 MB used, passed at 250–456 MB. Environmental, not an application defect — re-run the module alone to confirm. |

### Suggested roadmap

**Near term**
1. Extend the style hoister to the shells, if `safe_dom.js` is ever moved off
   `setAttribute('style')` onto CSSOM writes (which are exempt — §7.3.1). Until
   then the shell exception is accepted and CI-guarded.
2. Configure SMTP, or formally document admin-driven resets for staff.
3. Rehearse a full backup restore end to end.

**Medium term**
4. Converge on a single frontend.
5. Extend the XSS analyzer over the SPA **source** (the compiled bundle is
   audited; its source is not yet in the ratchet).
6. Add CI to run `pytest` + `scan_xss_sinks.py --check` on every push.
7. Migrate `safe_dom.js` from `setAttribute('style', …)` to per-property CSSOM
   writes, which would let the shells drop `style-src-attr 'unsafe-inline'` too.

**Longer term**
8. Two-factor authentication for admin accounts.
9. Candidate-facing status portal to cut status-chasing calls.
10. Automated government-portal integration where APIs exist.
